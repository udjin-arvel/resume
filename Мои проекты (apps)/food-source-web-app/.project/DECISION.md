# FoodSource — журнал решений (для ревью / HR)

Кратко: **почему сделано так**, а не иначе. Прототип по ТЗ «B2B decision helper для закупщика»; акцент — прозрачный скоринг и сравнение, не маркетплейс.

## 1. Архитектура

| Решение | Обоснование |
|---------|-------------|
| **Тонкий клиент + API** | Вся фильтрация, скоринг, бейджи и логика compare/recommend — на backend. UI только отображает ответы. Снижает расхождение с ТЗ и упрощает смену формулы без релиза фронта. |
| **Готовый UI в `client/`** | Фронт уже реализован (TanStack Start, Lovable). Бэкенд подключён под существующий контракт [`client/src/lib/api/client.ts`](../client/src/lib/api/client.ts), без переименования в `frontend/` из ТЗ. |
| **In-browser mock** | При отсутствии `VITE_API_URL` клиент использует `client/src/lib/api/mock/` — UI и Lovable-превью работают без сервера; контракт mock = контракт FastAPI. |
| **SQLite + идемпотентный сид** | Достаточно для ~20 записей и demo; сид при старте только если таблица пуста. Volume в Docker для сохранения данных между перезапусками. |

## 2. API и контракт

| Решение | Обоснование |
|---------|-------------|
| **Расширенный ответ относительно «голого» Supplier** | Клиент ожидает `score`, `score_reasons`, `score_breakdown`, `flags`, `rank_badge` — реализовано на backend, а не только поля из таблицы ТЗ. |
| **Query brief через `brief_*` в query** | Совпадает с тем, как [`api.client.ts`](../client/src/lib/api/client.ts) сериализует brief в GET `/suppliers`. |
| **Нет `GET /export`** | CSV формируется на клиенте вместе с заметками из localStorage — в ТЗ допускается; серверных user notes нет. |
| **POST `/compare` и `/recommend`** | Тела и ответы зеркалят mock (`best` как массивы id, explanation + weights в recommend). |

## 3. Скоринг

| Решение | Обоснование |
|---------|-------------|
| **Формула 0–100 = набранные / максимум × 100** | Как в mock: в знаменателе только критерии, релевантные текущему запросу; контакты и свежесть — всегда. |
| **Веса в конфиге (Python `DEFAULT_WEIGHTS`)** | Категория 30, регион 20, сертификаты 20, MOQ 15, бюджет 10, контакты 10, свежесть 5; порог устаревания 180 дней. |
| **Без brief — скор «полноты карточки»** | Чтобы в общем списке скоры не были одинаковыми у всех поставщиков. |
| **Бейджи** | С активным brief — один `best`; без brief — `top` у трёх лидеров по скору. |
| **Compare: MOQ/цена только при одной единице** | Кг и шт не сравниваются — как в mock и тестах клиента. |

## 4. UX / данные (скоуп ТЗ)

| Решение | Обоснование |
|---------|-------------|
| **Заметки и статусы в localStorage** | Явно вне скоупа: нет auth, персональные данные только в браузере. |
| **Пустые поля — «—» с тултипом** | Реализовано на клиенте (`NoData`, `Value`). |
| **Демо-сид с «дырами»** | 3–4 без контактов, 2–3 с устаревшим `source_date`, часть без MOQ/цены — для проверки флагов и empty states. |

## 5. Инфраструктура и доставка

| Решение | Обоснование |
|---------|-------------|
| **Docker Compose: 2 сервиса** | Backend — production-like uvicorn; frontend в образе — **dev-сервер Vite** для быстрого demo (осознанный компромисс прототипа). |
| **`VITE_API_URL=http://localhost:8000` в Docker** | Браузер на машине пользователя, не сеть контейнеров; CORS на backend под localhost/8080. |
| **Порт UI 8080 в compose** | Согласован с дефолтом Lovable/Vite в этом проекте (не 5173 из абстрактного ТЗ). |
| **`demo.gif`** | Сгенерирован скриптом [`scripts/generate_demo_gif.py`](../scripts/generate_demo_gif.py) (Pillow) — два кадра «список + сравнение»; пересборка: `make demo-gif`. |
| **Этапы = отдельные git-коммиты** | client → seed → list/meta → compare/recommend → docker/README — проще ревью diff по частям. |

## 6. Тестирование

| Решение | Обоснование |
|---------|-------------|
| **pytest на backend** | Скоринг, фильтры, compare/recommend, идемпотентность сида — ориентир на [`scoring.test.ts`](../client/src/lib/api/mock/scoring.test.ts). |
| **vitest на client** | Mock-слой и роутинг; регрессия UI-контракта без e2e в CI прототипа. |

## 7. Осознанно не делали (скоуп ТЗ)

- Авторизация, парсинг сайтов, ML, отзывы, платежи  
- CRM, серверные заметки, настраиваемые веса в UI  
- Production-сборка фронта в текущем `docker-compose.yml` (описано в [DEPLOY.md](DEPLOY.md))

## 8. Что бы сделали при продолжении

1. PostgreSQL + Alembic, отказ от сида-only данных.  
2. Multi-stage Docker для UI (`npm run build` + nginx).  
3. OpenAPI как единственный источник типов для клиента (codegen).  
4. E2E (Playwright) на сценарии приёмки из ТЗ.
