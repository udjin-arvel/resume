# SPEED/O/METER

Веб-морда к той же задаче, что и CLI в корне репозитория: вбиваешь URL, гоняешь его несколько раз подряд, смотришь время, объём и скорость.

Это не «спидтест провайдера». Мы качаем конкретный файл и считаем, сколько байт пришло и сколько это заняло. Keep-alive обычно живой, поэтому первый запрос часто медленнее остальных — в сводке они разделены.

## Как запустить

Нужен Node 20+. Из этой папки:

```
npm i
npm run dev
```

Откроется Vite, обычно `http://localhost:3000`. Сборка: `npm run build`, потом `npm run preview`.

Зависимости крутятся вокруг TanStack Start + React. Логика замера лежит отдельно от UI: `src/lib/speed/`.

## Что происходит по кнопке

Форма — те же штуки, что флаги у CLI: URL, count, timeout в миллисекундах, retries, cache-bust.

Дальше браузер **сам ничего не качает**. Каждый запрос уходит на серверную функцию (`measureOnce`), та уже делает `fetch` и читает тело до конца. Так обходим CORS и не упираемся в то, что страница с localhost не имеет права ходить на чужой CDN.

Запросы строго по очереди. Пока идёт серия, можно нажать стоп — текущий дождётся, следующие не стартуют. Слева сыпятся строки по каждому запросу (ок / ретрай / fail), справа сводка: среднее, медиана, первый vs остальные, тело / заголовки / всего, скорость сразу в MB/s и Mbps.

Ретраи: сеть, таймаут, 5xx и 429. Обычные 4xx сразу fail. Редиректов не больше пяти. Таймаут режет весь запрос, не только коннект. Cache-bust дописывает `?cb=...` к исходному URL.

Единицы как в CLI: 1 MB = 10⁶ байт. Скорость считается только по телу, заголовки в неё не входят.

## Где цифры врут

В браузере (и в `fetch`) нет нормального доступа к байтам «по проводу» до gzip/br и к сырым заголовкам. Здесь просим `identity`, размер тела — то, что отдал `fetch`, заголовки собираем из того, что видно в `Response`. Для картинки без сжатия это близко к CLI, для сжатого JSON — уже оценка.

Если нужны wire-байты как есть — корневой `node dist/index.js <url>`.
