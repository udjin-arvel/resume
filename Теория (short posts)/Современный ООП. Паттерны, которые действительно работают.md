## Современное ООП: объекты, границы и паттерны, которые действительно работают

ООП прошло долгий путь: от "всё есть класс" до "давайте всё же будем практичными". Его придумали не для того, чтобы разработчики бесконечно наращивали иерархии классов, вставляя абстракции везде, где только можно, а для управления возрастающей сложностью кода.

Под "управлять сложностью" я имею в виду разумно распределять ответственность, защищать инварианты и гибко управлять зависимостями.

#### Утро с ООП начинается не с наследования

Представим себе простой класс:

```ts
class Order {
  public status: string = "draft";
  public items: { price: number; quantity: number }[] = [];
}
```

По всем признакам это класс, вот только он почти ничего не делает и ничего не контролирует. Написали мы `order.status = "super_mega_purchase"`, и кто это проверит? Вопрос в небо. Если модель не защищает собственные инварианты, она почти бесполезна.

Куда полезнее выглядит так:

```ts
type OrderStatus = "draft" | "pending" | "paid";

type OrderPurchase = Readonly<{
  productId: number;
  price: number;
  quantity: number;
}>;

class Order {
  #status: OrderStatus = "draft";
  #purchases: OrderPurchase[] = [];

  constructor(public readonly id: string) {}

  addPurchase(purchase: OrderPurchase): void {
    if (this.#status !== "draft") {
      throw new Error("Заказ уже оформлен");
    }

    if (purchase.price <= 0 || purchase.quantity <= 0) {
      throw new Error("Цена и количество должны быть положительными");
    }

    this.#purchases.push(purchase);
  }

  place(): void {
    if (this.#purchases.length === 0) {
      throw new Error("Нельзя оформить пустой заказ");
    }

    this.#status = "pending";
  }

  markPaid(): void {
    if (this.#status !== "pending") {
      throw new Error("Оплатить можно только оформленный заказ");
    }

    this.#status = "paid";
  }

  get totalPrice(): number {
    return this.#purchases.reduce((total, purchase) => {
      return total + purchase.price * purchase.quantity;
    }, 0);
  }

  get status(): OrderStatus {
    return this.#status;
  }
}
```

В этом случае объект не только хранит поля, но и описывает доступные переходы состояния. Он контролирует собственные правила, которые нельзя нарушить извне. В этом и есть практический смысл инкапсуляции.

> Не каждому набору данных нужен класс. DTO, конфиги и простые ответы API вполне могут оставаться обычными структурами.



#### Интерфейс - это контракт, а не обязательный атрибут класса

Интерфейс определяет роль, которую объект играет в системе. Он не обязан дублировать имя конкретного класса и вообще не должен появляться просто "для красоты".

Для примера рассмотрим уведомления:

```ts
interface Notifier {
  send(recipient: string, message: string): Promise<void>;
}

class ConsoleNotifier implements Notifier {
  async send(recipient: string, message: string): Promise<void> {
    console.log({ recipient, message });
  }
}

const notifier: Notifier = new ConsoleNotifier();

await notifier.send("user@example.com", "Ваш заказ оформлен");
```

Бизнес-логике здесь не нужно знать, как именно отправляются уведомления. Конкретная реализация выбирается снаружи: email-сервис, SMS-провайдер, push-уведомления или обычный вывод в консоль. Сценарий не зависит от канала связи, ему нужна только роль: возможность уведомить клиента.

Интерфейс полезен на границах приложения, когда одна самостоятельная часть кода взаимодействует с другой. Его задача - разорвать прямую зависимость от логически независимой детали. Если хочется зафиксировать такую границу, значит, время интерфейса действительно пришло.

#### Абстрактный класс нужен, когда общий алгоритм правда существует

Интерфейс описывает, что объект умеет делать, а абстрактный класс уже может содержать реализацию или общее состояние.

Разберем стандартный пример с импортером данных:

```ts
type ImportRow = {
  email: string;
};

abstract class DataImporter {
  async import(source: string): Promise<number> {
    const rows = this.parse(source);

    this.validate(rows);
    await this.save(rows);

    return rows.length;
  }

  protected abstract parse(source: string): ImportRow[];

  protected validate(rows: ImportRow[]): void {
    if (rows.length === 0) {
      throw new Error("Нет данных для импорта");
    }
  }

  protected abstract save(rows: ImportRow[]): Promise<void>;
}
```

Этот паттерн называется Template Method, или "шаблонный метод": базовый абстрактный класс задает основной алгоритм действий, а наследники реализуют конкретные шаги.

Абстрактный класс уместен, когда общий алгоритм стабилен и может переиспользоваться, а наследники выполняют одну и ту же роль, не обрастая бесконечными проверками:

```ts
if ("это здесь не подходит") {
  throw new Error("ну и дела");
}
```

А если видите конструкцию вроде этой:

```ts
if (this instanceof SuperRareSpecialAdditionalImporter) {
  // ...
}
```

то, скорее всего, абстракция уже не помогает, а мешает.

Абстрактный класс - это про гибкость внутри алгоритма и постоянство снаружи. Он нужен, когда части алгоритма меняются независимо, но отношения между типами остаются устойчивыми.

#### Adapter переводит внешний контракт на язык приложения

Адаптер нужен для "перевода" контракта внешнего API или SDK на язык вашего приложения. Внешний сервис может использовать другие названия полей, другие форматы и другие правила. Бизнес-код не должен знать эти детали.

Распространенный пример с платежами:

```ts
type PaymentRequest = {
  orderId: string;
  price: number;
};

interface PaymentGateway {
  charge(request: PaymentRequest): Promise<{ paymentId: string }>;
}

// Сторонний SDK
interface ExternalPaymentSdk {
  createCharge(input: {
    merchant: string;
    amount: number;
  }): Promise<{ transaction_id: string }>;
}

// Адаптер
class ExternalPaymentSdkAdapter implements PaymentGateway {
  constructor(private readonly sdk: ExternalPaymentSdk) {}

  async charge(request: PaymentRequest): Promise<{ paymentId: string }> {
    const result = await this.sdk.createCharge({
      merchant: request.orderId,
      amount: request.price,
    });

    return { paymentId: result.transaction_id };
  }
}
```

Хороший адаптер может переводить внешние ошибки во внутренние, преобразовывать форматы и проверять ответы стороннего API. Но он не должен незаметно принимать бизнес-решения: например, добавлять скидку к `request.price`.

Важно и другое: адаптер не должен скрывать различия между формой и семантикой внешнего API. Метод `authorize` в платежном шлюзе может означать как простую проверку карты, так и полноценную заморозку средств. Если адаптер замаскирует это различие красивым, но неверным контрактом, проблема все равно догонит вас позже.

#### Strategy выносит изменяемый алгоритм

Стратегия полезна для тарифов, скидок, маршрутизации, разных способов авторизации или выбора способа обработки данных.

Пример со скидками:

```ts
interface PricingStrategy {
  calculate(base: number): number;
}

class RegularPricing implements PricingStrategy {
  calculate(base: number): number {
    return base;
  }
}

class BlackFridayPricing implements PricingStrategy {
  calculate(base: number): number {
    return base * 0.5;
  }
}

class Cart {
  constructor(private readonly pricing: PricingStrategy) {}

  total(base: number): number {
    return this.pricing.calculate(base);
  }
}
```

Код, который использует корзину, не меняется. Меняется только стратегия расчета. Это и есть главный смысл паттерна: заменить ветвление вида `if (blackFriday) ...` на объект с понятным контрактом.

#### Facade дает простой вход в сложную подсистему

Фасад предоставляет удобный интерфейс к сложной подсистеме.

Упрощенный пример:

```ts
interface Validator {
  validate(order: Order): Promise<void>;
}

interface OrderRepository {
  save(order: Order): Promise<void>;
}

class OrderFacade {
  constructor(
    private readonly validator: Validator,
    private readonly orderRepository: OrderRepository,
  ) {}

  async place(order: Order): Promise<{ orderId: string }> {
    await this.validator.validate(order);

    order.place();
    await this.orderRepository.save(order);

    return { orderId: order.id };
  }
}
```

Снаружи виден только метод `place`. Это удобно, но стоит помнить, что фасад не делает операции атомарными. Если вызвать подряд:

```ts
await payment.charge(...);
await orders.save(...);
await notifications.send(...);
```

это не станет единой транзакцией. Списание могло произойти, а заказ из-за ошибки не сохранился. Или заказ сохранился, но уведомление не отправилось. Фасад упрощает интерфейс, но не отменяет сложность системы, поэтому на практике нужны идемпотентность, промежуточные состояния и обработка сбоев.

#### Repository прячет детали хранения данных

Repository нужен, когда бизнес-коду важно работать с сущностями, а не знать, где и как они лежат: в PostgreSQL, Redis, HTTP API, local storage или вообще в памяти для тестов.

Пример:

```ts
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

class PostgresOrderRepository implements OrderRepository {
  constructor(private readonly db: DatabaseClient) {}

  async findById(id: string): Promise<Order | null> {
    const row = await this.db.orders.findOne({ id });

    if (!row) {
      return null;
    }

    return OrderMapper.toDomain(row);
  }

  async save(order: Order): Promise<void> {
    await this.db.orders.upsert(OrderMapper.toPersistence(order));
  }
}
```

Важный момент: репозиторий - это не просто "класс для SQL-запросов". Его смысл в том, чтобы скрыть инфраструктурные детали и вернуть доменную модель в нормальном виде. Поэтому наружу лучше не выпускать ORM-сущности, сырые строки таблиц и технические поля, которые не относятся к бизнес-логике.

Плохой репозиторий заставляет приложение думать таблицами. Хороший репозиторий позволяет приложению думать заказами, пользователями, платежами и другими сущностями предметной области.

#### Decorator добавляет поведение, не меняя контракт

Декоратор реализует тот же контракт, что и базовый объект, но добавляет дополнительное поведение.

Например, это полезно для логирования или измерения времени:

```ts
class TimingNotifier implements Notifier {
  constructor(private readonly notifier: Notifier) {}

  async send(recipient: string, message: string): Promise<void> {
    const startAt = performance.now();

    try {
      await this.notifier.send(recipient, message);
    } finally {
      console.log({
        operation: "notification.send",
        duration: performance.now() - startAt,
      });
    }
  }
}
```

Важно помнить, что обертка не должна ломать поведение основной операции. А все опасные действия вроде списания денежных средств должны быть идемпотентны, иначе повторная попытка или дополнительный слой обвязки быстро превращаются в источник багов.

#### Factory собирает объект, когда создание становится отдельной ответственностью

Фабрика помогает создать объект, если он зависит от специфичной конфигурации или требует собрать зависимости.

На одном из предыдущих мест работы у меня была дашборд-панель для IPTV-контента. В самом начале, когда нужно было получить общий объект медиа, детали сборки писали прямо в клиентском коде:

```php
function getMediaObject(int $id, array $media): Media
{
    if ($media['type'] === 'series') {
        $seasons = getSeasons($media['id']);

        return new Series(
            $media['id'],
            $media['title'],
            $media['poster'],
            $seasons,
        );
    }

    // ...
}
```

Понятное дело, такое себе: клиент не должен знать, как именно создается контент. Поэтому мы вынесли сборку в фабрики:

```php
interface MediaFactory
{
    public function create(RawMediaDto $raw): Media;
}

final class ChannelFactory implements MediaFactory
{
    public function __construct(
        private readonly EpgProvider $epg,
        private readonly DrmResolver $drm,
    ) {}

    public function create(RawMediaDto $raw): Media
    {
        return new Channel(
            $raw->id,
            $raw->title,
            $raw->poster,
            $raw->stream,
            $this->epg,
            $this->drm,
            $raw->requiredSub,
            $raw->regions,
        );
    }
}

final class VideoFactory implements MediaFactory
{
    public function __construct(
        private readonly CdnResolver $cdn,
        private readonly SubtitleService $subtitles,
        private readonly AudioService $audio,
        private readonly DrmResolver $drm,
    ) {}

    public function create(RawMediaDto $raw): Media
    {
        $manifest = $this->cdn->resolve($raw->stream);
        $subs = $this->subtitles->forMedia($raw->id);
        $audios = $this->audio->forMedia($raw->id);

        return new Video(
            $raw->id,
            $raw->title,
            $raw->poster,
            $manifest,
            $raw->duration,
            $subs,
            $audios,
            $this->drm,
            $raw->ageRating,
        );
    }
}

final class SeriesFactory implements MediaFactory
{
    public function __construct(private readonly SeriesService $series) {}

    public function create(RawMediaDto $raw): Media
    {
        $seasons = $this->series->getSeasons($raw->id);

        return new Series(
            $raw->id,
            $raw->title,
            $raw->poster,
            $seasons,
            $raw->ageRating,
        );
    }
}
```

А дальше остается выбрать нужную фабрику:

```php
$factory = match ($raw->type) {
    'vod' => $videoFactory,
    'series' => $seriesFactory,
    'channel' => $channelFactory,
};

$mediaObject = $factory->create($raw);
```

Фабрика полезна, когда создание объекта стало сложнее самого `new`. Но если объект создается одной строкой и без условий, отдельная фабрика только добавит шума и ненужной сложности.

#### Builder помогает собрать сложный объект пошагово и наглядно

Builder нужен, когда объект имеет много параметров и часть из них опциональна, при том, что сборка должна остаться читаемой. Особенно это заметно в тестах, конфигурациях и объектах-запросах вроде того же Query Builder или laravel.

Представьте создание отчета:

```ts
type ReportFormat = "pdf" | "xlsx";

class ReportRequest {
  constructor(
    public readonly from: Date,
    public readonly to: Date,
    public readonly format: ReportFormat,
    public readonly includeDrafts: boolean,
    public readonly recipients: string[],
  ) {}
}
```

Можно каждый раз вызывать конструктор с пятью аргументами и надеяться, что никто не перепутает `from` и `to`. А можно сделать сборку явной:

```ts
class ReportRequestBuilder {
  #from: Date = new Date();
  #to: Date = new Date();
  #format: ReportFormat = "pdf";
  #includeDrafts = false;
  #recipients: string[] = [];

  period(from: Date, to: Date): this {
    this.#from = from;
    this.#to = to;
    return this;
  }

  asXlsx(): this {
    this.#format = "xlsx";
    return this;
  }

  withDrafts(): this {
    this.#includeDrafts = true;
    return this;
  }

  sendTo(email: string): this {
    this.#recipients.push(email);
    return this;
  }

  build(): ReportRequest {
    if (this.#from > this.#to) {
      throw new Error("Начало периода не может быть позже конца");
    }

    return new ReportRequest(
      this.#from,
      this.#to,
      this.#format,
      this.#includeDrafts,
      this.#recipients,
    );
  }
}

const request = new ReportRequestBuilder()
  .period(new Date("2026-01-01"), new Date("2026-01-31"))
  .asXlsx()
  .withDrafts()
  .sendTo("manager@example.com")
  .build();
```

Builder делает создание сложного объекта более прозрачным и наглядным, а все проверки собирает в одном месте. Но, если билдер просто повторяет сеттеры без правил и смысла, это не паттерн, а выстрел в свою ногу.

#### Вместо заключения

Современное ООП - это не про наследование и не про "всё есть объект". Это про управление зависимостями и изменениями. Абстрактные классы, интерфейсы, фасады, адаптеры, стратегии, репозитории и билдеры - это инструменты, которые помогают писать код, который легко тестировать, менять и понимать другим людям.

Главное правило старо, как мир: паттерн нужен только тогда, когда он решает конкретную боль. Если боли нет, простота важнее архитектурной красоты.
