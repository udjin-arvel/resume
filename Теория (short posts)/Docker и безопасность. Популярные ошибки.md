## Docker и безопасность: популярные ошибки

Docker очень сильно упростил сборку и доставку приложений, и спасибо ему за это, но за удобство часто приходится платить. В данном случае плата взимается в виде ложного ощущениея изоляции. Контейнер воспринимают как маленькую виртуальную машину, когда это не так. Мол, что бы внутри ни произошло, хост сервера это не затронет. Но на деле контейнеры используют то же ядро Linux, что и хост, а граница между приложением и вашей тачкой держится на хрупких плечах namespaces и cgroups (механизм распределения ресурсов машины), capabilities (разделение привелегий), seccomp (ограничение системных вызовов syscalls), ну и, конечно, правильной конфигурации самого Docker.

Поэтому большая часть проблем с безопасностью возникает не из-за какого-нибудь хитрого  "эксплойта судного дня" (zero-day), а из-за вполне себе бытовых вещей: забыли переключиться с root на docker пользователя, случайно положили токен или секрет в образ, открыли порт наружу через 0.0.0.0 или смонтировали `docker.sock`, потому что в моменте так было удобнее.

Давайте же разберём наиболее популярные ошибки, которые я чаще всего встречал в Dockerfile, compose-файлах и конфигурации серверов на протяжении своей карьеры в качестве devOps-инженера (помимо основной занятости web-разработчиком).  
И начнем мы с классики:

#### Секреты внутри образа

Токен передают через `ARG`, записывают во временный файл, используют при установке зависимостей, а затем файл удаляют:

```
FROM node:22

ARG NPM_TOKEN
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > ~/.npmrc
RUN npm ci
RUN rm ~/.npmrc
```

Каждая инструкция создаёт новый слой. Удаление файла/строчки на последнем слое не удалит его из истории образа (файлы вообще не удаляются, а "белятся", помечаются специальным whiteout-маркером на удаление). С `ENV` ситуация ещё очевиднее: значение останется в конфигурации контейнера и параметр будет прекрасно видно через `docker inspect` или `docker history`.

Для секретов, которые нужны только во время сборки, в BuildKit есть secret mounts, так что используйте его:

```
# syntax=docker/dockerfile:1
FROM node:22

RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
```

```
docker build --secret id=npmrc,src=$HOME/.npmrc -t myapp .
```

Секрет будет доступен только во время выполнения конкретной инструкции и не попадёт в слой. А пароли и ключи вообще не должны участвовать в сборке - используйте Docker Secrets, Vault или какой-нибудь другой менеджер секретов.

#### В контекст сборки попадает весь проект

Команда `COPY . .` удобна, но без `.dockerignore` вместе с кодом в контекст сборки отправятся и `.git`, и локальный `.env`, и ваши приватные ключи, логи, кэш и тд и тп. Даже если Dockerfile не копирует часть этих файлов в финальный образ, они всё равно передаются демону и могут случайно оказаться в одном из промежуточных слоёв, так что не пренебрегайте `.dockerignore` .

Пример`.dockerignore`:

```
.git
.env
.env.*
*.pem
id_rsa
node_modules
.venv
__pycache__
*.log
```



#### `latest`, старые версии и слишком большие образы

Строчка `FROM node:latest` - это не гарантия стабильности и безопасности, а настоящая лотерея. Сегодня ваша сборка работает идеально, а через месяц авторы nodejs обновляют этот тег, добавляя туда последнюю версию. По итогу, когда вы запускаете сборку заново, Docker скачивает *уже другой* образ под тем же именем `latest`, и в коде что-то ломается, а проект "падает". Результат становится невоспроизводимым.

Версию базового образа стоит фиксировать хотя бы до конкретного релиза:

```
FROM node:22.12.0-bookworm-slim
```

Для сборок, где важна строгая воспроизводимость, образ фиксируют по дайджесту.  
PS: правда тогда он сам по себе не обновится, поэтому вам придется регулярно смотреть и проверять новые версии, иначе уже через год ваш образ превратиться в кладбище известных уязвимостей.

Другая крайность - ставить полноценный ubuntu-образ и запихивать в него половину репозитория ради одного приложения. Чем больше пакетов, тем больше поверхность атаки и тем сложнее понять, откуда приехала очередная уязвимость. Обычно хватает `slim`-образа или multi-stage сборки, где dev-зависимости остаются на первом этапе, а в итоговый образ попадают только необходимые файлы.

`alpine` и distroless тоже полезны, но использовать их не глядя тоже не стоит. Alpine основан на musl вместо glibc, из-за чего некоторые библиотеки работают иначе, а отладка distroless-контейнера без shell весьма неудобна. Минимальный образ должен оставаться совместимым с приложением и быть практичным, а не просто красиво выглядеть в каком-нибудь отчётике.

#### Запуск приложения от root

Если в Dockerfile не указан `USER`, процесс обычно запускается от UID 0 то есть от рута. Конечно, root внутри контейнера не всегда то же самое, что root на хосте, но при наличии уязвимостей или опасном монтировании это всё равно может упростить злоумышленнику выход за границы контейнера.

Непривилегированного пользователя лучше создать прямо в образе:

```
FROM node:22-alpine

WORKDIR /app
RUN addgroup -S app && adduser -S app -G app # эта строка

COPY --chown=app:app package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --chown=app:app src/ ./src/

USER app
CMD ["node", "src/server.js"]
```

После сборки это легко проверить командой id или whoami:

```
docker run --rm myapp id
```



#### `--privileged` и лишние права

Флаг `--privileged` почти стирает границу между контейнером и хостом: открывает устройства, расширяет до максимума capabilities и отключает часть защитных профилей. Если приложение требует этот флаг просто для запуска, сперва стоит разобраться, какое именно право ему нужно.

Чаще всего достаточно добавить одну capability, а остальные убрать:

```
docker run \
  --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE \
  --security-opt=no-new-privileges \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  myapp
```

Здесь корневая файловая система доступна только для чтения, временные данные пишутся в отдельный кусочек оперативной памяти в `tmpfs`, а процесс не может получить новые привилегии.  
PS: не надо бездумно копировать эту команду, сначала выясните, какие системные возможности вашему приложению действительно нужны.

#### Смонтированный `docker.sock`

Монтирование `/var/run/docker.sock` часто встречается в CD/CI, панелях управления и контейнерах мониторинга:

```
docker run -v /var/run/docker.sock:/var/run/docker.sock my-tool
```

Проблема в том, что доступ к сокету фактически равен root-доступу на хосте. Контейнер может попросить демон запустить другой контейнер с `--privileged`, смонтировать в него `/` и получить всю файловую систему сервера целиком (получал на практике именно этот сценарий). Суффикс `:ro` при этом почти ничего не дает: он запрещает запись в сам файл сокета, но не запрещает отправлять демону команды.

Лучший вариант - не передавать сокет вообще. Для сборки образов можно использовать rootless BuildKit, Buildah или отдельный изолированный runner.

Ещё опаснее открыть Docker API на `0.0.0.0:2375` без TLS. Это уже прям готовая точка входа на сервер. Для удалённой работы лучше использовать ssh-подключение или TLS с проверкой клиентских сертификатов.

#### Порты и сети

Команда ниже по умолчанию публикует порт на всех интерфейсах (подставляется как 0.0.0.0:5432):

```
docker run -p 5432:5432 postgres
```

Если файервол не настроен, то база данных окажется доступна снаружи любому желающему, и тогда сложный пароль - ваш последний слой обороны. Когда сервис нужен только внутри хоста, адрес лучше указать явно:

```
docker run -p 127.0.0.1:5432:5432 postgres
```

или в docker-compose.yml:

```
ports:
      - "127.0.0.1:5432:5432"
```

Если база нужна только другому контейнеру, публиковать порт вообще не требуется. Оба сервиса можно подключить к отдельной bridge-сети и обращаться к базе по имени контейнера.

#### Отсутствие лимитов

Контейнер без лимитов может сожрать всю доступную память, породить тысячи процессов или вытеснить процессы с CPU. Это может произойти и без атаки: достаточно утечки памяти в вашем приложении.

Для обычного `docker run` лимиты задаются явно:

```
docker run -d \
  --memory=512m \
  --memory-swap=512m \
  --cpus=1.0 \
  --pids-limit=100 \
  myapp
```

Не берите готовые значения, померьте вашу нагрузку и возьмите с запасом: важно, чтобы ограничения вообще существовали, а мониторинг сообщал о приближении к ним до того, как контейнер начнёт рестартиться по OOM.

#### Секреты во время работы приложения

Переменная окружения удобна, но сама по себе не является защищенным хранилищем секретов. Значение может всплыть в `docker inspect`, в диагностическом дампе или логах CD/CI. Ещё хуже, когда приложение при старте печатает всю конфигурацию в вывод stdout, а затем эти логи годами лежат в файловой системе.

Для локальной разработки `.env` вполне приемлем (если, конечно, файл исключён из git). В продакшене лучше монтировать секрет как файл из менеджера секретов и давать доступ только нужному процессу. Docker Secrets подходит для Swarm; в обычном Compose есть секция `secrets, которая` в основном помогает аккуратно смонтировать файл, но всё еще не превращает его в защищённое внешнее хранилище (но на практике обычно этого хватает).

PS: не забывайте, что удаление секрета из текущей версии репозитория не удаляет его из истории. Если пароль или секрет уже был закоммичен или попал в лог, его надо перевыпустить (переписывание git-истории здесь лишь уборка следов).

#### Что проверить в существующем проекте

Если нужно быстро оценить незнакомый проект, я бы шёл примерно в таком порядке:

1. Посмотрите, от какого пользователя запущен процесс и есть ли в Dockerfile инструкция `USER`.
2. Проверьте Dockerfile и историю образа на токены, пароли и приватные ключи.
3. Откройте `.dockerignore` и посмотрите, не копируется ли в образ весь репозиторий.
4. Нашёл все кейсы `--privileged`, `cap_add`, `network_mode: host` и возможные отключения seccomp/AppArmor.
5. Проверьте монтирование `docker.sock`, корня хоста и общих writable-томов (volumes).
6. Посмотрите, на каких адресах опубликованы базы данных, очереди и какие-нибудь cli.
7. Проверьте лимиты на память, на CPU, на количество процессов.
8. Запустите сканирование образа и убедился, что базовая ОС ещё поддерживается и не имеет известных уязвимостей.
9. Посмотрите, откуда приложение получает секреты и не выводит ли оно их случайно в лог.

#### Вместо заключения

Безопасный контейнер получается не из одной волшебной настройки "make it secure, buddy", а из нескольких скучных и унылых ограничений: меньше файлов в образе, меньше прав у процесса, меньше открытых портов и никаких секретов нигде. В этом и состоит основной принцип - контейнер должен получать ровно столько доступа, сколько ему необходимо для работы, и ни строчкой больше. Запомните основной принцип: минимизируйте поверхность атаки на каждом этапе.

Если времени нет или вам просто лень, начните с трёх простых вещей: перестаньте запускать приложение от root, уберите секреты из образов и проверьте, где смонтирован `docker.sock`. Эти ошибки встречаются чаще всего (сам попадался), и дают условному хакеру самые неприятные возможности. Остальные меры уже наращивайте сверху: read-only файловая система, capabilities, лимиты, сетевые ограничения и регулярные обновления образов.
