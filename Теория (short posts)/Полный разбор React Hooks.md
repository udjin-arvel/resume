## Полный разбор React Hooks

React Hooks появились в далеком 2019 году и с тех пор стали основным API для классовых компонентов, наследующих React.Component. Они были призваны решить три насущные проблемы старых react-компонентов, и мы коротко рассмотрим каждую из этих проблем:

#### Проблема 1. Фрагментация логики по lifecycle-методам.

Раньше, одна и та же задача, например, получение данных или подписка на WebSocket вынужденно разбивалась по нескольким lifecycle-методам - componentDidMount для запуска ws или получения данных из API, componentDidUpdate для какого-нибудь изменения фильтров и componentWillUnmount для очистки ws и кэша. Логика одной и той же задачи получалась разорванной, и, чтобы понять - как работает код, приходилось читать весь файл, где lifecycle-методы могли быть еще и разбросаны далеко друг от друга, что быстро превращалось в жгучую боль в определенном месте.

#### Проблема 2. "Обёрточный ад" и render props.

До хуков единственным способом переиспользовать логику состояний вашего приложения были компоненты HOC (т.е. Higher-Order Components), это когда вы заворачиваете компонент в функцию-обертку, которая передает внутрь необходимые пропсы. На выходе получался тот самый "обёрточный ад". А рядом ещё шёл такой же render props - компоненты, которые принимали функцию рендера, как пропс. Уже из определений ясно какой хаос возникал с наслоением подобных абстракций друг на друга. Простой Header-компонент превращался в слоёный пирог, где каждый слой размазывался на десятки строк однотипного кода. Минусы этого очевидны.

Вот пример классического "wrapper hell":

```
export default withAnalytics(
  withTheme(
    withTranslation(
      withAuth(
        withUser(
          withRouter(ProfilePage)
        )
      )
    )
  )
);
```

> PS: render props выглядели примерно так же, только пирамида в виде функций-колбэков выглядела еще массивнее.

**Проблема 3. Нагрузка от this:** немного в стороне шла проблема контекста this, в классовых компонентах this вёл себя зачастую контринтуитивно, приходилось постоянно прописывать bind, чтобы явно контролировать контекст. А чтобы использовать текущее значение из какого-нибудь this.props или this.state приходилось сохранять это значение в локальную переменную (нередко ты видел столбики таких переменных, в одной функции за другой).

Каждую из этих проблем и был призван решить useEffect и другие хуки. Однако на смену этим проблемам пришли другие, но прежде чем говорить о них, давайте зафиксируем корректную ментальную модель хуков, то есть ответим на вопрос "как правильно думать о хуках?".

Предлагаю вашему вниманию три коротких тейка:

1. Хуки зависят от порядка вызова, ведь React хранит их в связанном списке (структура Linked List, где каждый хук - объект Hook Node). Более того, React полагается на порядок хуков для корректного сохранения состояний между рендерами, и, если между рендерами количество хуков разное, он бросит вам ошибку "more hooks than expected" и откажется рендерить компонент.
  > PS: сколько же я намучился в свое время, выясняя где находится этот чёртов условный хук, мне пришлось написать счетчик хуков и компонентов только для того, чтобы понять, что он лежал в стороннем компоненте... so sad. Поэтому, пожалуйста, не вызывайте хуки условно или в циклах, это нарушает порядок между вызовами.
2. Эффекты — это синхронизация, а не lifecycle. Иными словами: это не про "запустить код при mount", это про синхронизировать ваше состояние с внешними источниками данных.
3. Мемоизация нужна для предотвращения лишнего ререндера дочерних компонентов (т.е. не только и не столько для оптимизации тяжелых вычислений, keep it in your mind, pal).

Зная это, теперь уже можно поговорить о распространенных ошибках, которые я часто видел в том числе и на своих проектах:

**1. Derived state или контроль состояния через useEffect:** разработчики (и я тоже было дело, что уж) часто кладут в state то, что можно вычислить напрямую из существующих пропсов или другого стейта, а затем синхронизируют состояние через useEffect, что вызывает двойной рендер.

Простой пример:

```
function ItemList({ items }) {
  const [searchTitle, setSearchTitle] = useState("");
  const [filteredItems, setFilteredItems] = useState([]);

  useEffect(() => {
    setFilteredItems(items.filter(i => i.title.includes(search)));
  }, [items, searchTitle]);

  return <div>{filteredItems.map(i => <p key={i.id}>{i.title}</p>)}</div>;
}
```

В итоге: React сначала рендерит компонент один раз с начальным состоянием, затем useEffect обновляет стейт ещё раз через setFilteredItems и снова происходит рендер.

Или пример попроще:

```
function Profile({ firstName, lastName }) {
  const [fullName, setFullName] = useState("");

  useEffect(() => {
    setFullName(`${firstName} ${lastName}`);
  }, [firstName, lastName]);

  return <h1>{fullName}</h1>;
}
```

Здесь происходит то же самое с повторным ререндером.

В первом случае правильнее было бы описать переменную через useMemo, не заводя переменную setFilteredItems вообще:

```
const filteredUsers = useMemo(
  () => users.filter(u => u.name.includes(search)),
  [users, search]
);
```

А во втором сразу записать полное имя в переменной:

```
const fullName = `${firstName} ${lastName}`;
```

**2. Stale closures или пропущенные зависимости:** если не указать динамическую переменную в хуке, React не обновит ваше состояние.

То есть в случае:

```
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => {
    console.log(count); // Здесь count всегда будет 0, ведь состояние не обновляется, хук замкнул изначальный 0, вызвался один раз и так с ним и остался
  }, 1000);
  return () => clearInterval(id);
}, []); // Здесь не указали count, как переменную обновления
```

**3. Бесконечные циклы из-за обновления состояний в хуках:** функции и объекты создают новую ссылку на участок памяти при каждом рендере, новая ссылка - новый рендер, и так по кругу.

Быстрый пример:

```
const doNothing = () => {};
useEffect(() => doNothing(), [doNothing]); // первый рендер + ссылка №1 -> сработал хук -> второй рендер + ссылка №2 -> сработал хук -> ...
```

Вместо этого пишите логику прямо в хуке или используйте useCallback.

**4. Отсутствие очистки (cleanup):** если не записать в return хука метод очистки, то все критичные эффекты так и останутся в памяти. Если с какими-нибудь событиями на элементе всё не так страшно (при ближайшем сборе мусора js сам очистит обработчик, если соответствующий DOM-элемент был удален), то в следующем примере мы уже получаем утечку памяти:

```
useEffect(() => {
  const intervalId = setInterval(() => {}, 1000);
  // Нет cleanup - интервал остался в памяти и продолжает работать, потребляя ресурсы
}, []);
```

Правильно с очисткой:

```
useEffect(() => {
  const intervalId = setInterval(() => {}, 1000);
  return () => clearInterval(intervalId);
}, []);
```

В целом придерживайтесь правила, что если эффект что-то запускает - интервал, таймер, запрос на подписку или обновление данных, - то должен уметь это что-то и остановить.

**5. Гонки состояний при асинхронных запросах:** если в useEffect есть часто сменяемый пропс, который используется в асинхронном вызове, то может сложиться ситуация, что новый запрос придет перед старым. К примеру:

```
useEffect(() => {
  fetchUser(userId).then(setUser);
}, [userId]); // Если userId здесь меняется часто, например быстро щелкаем по окнам данных пользователей, то запросто можем после загрузки данных получить в окне данные от предыдущего пользователя, а не текущего выбранного.
```

Правильнее было бы в этом случае иметь механизм отмены предыдущего запроса, чтобы при ререндерах он останавливался:

```
useEffect(() => {
  let cancelled = false; // или AbortController вместо флага

  fetchUser(userId).then(data => {
    if (!cancelled) setUser(data);
  });

  return () => { cancelled = true; };
}, [userId]);
```

Также можно отметить случаи, когда разработчики пишут синхронный setState в хуке. Был случай, когда инициализировали состояние загрузки данных, как const [loading, setLoading] = useState(false), а потом сразу в хуке писали setLoading(true), что стартовало еще один ререндер, а в конкретном случае это еще мигание загрузчика давало, что, понятное дело, такой себе ui/ux.

Дополнительно оставлю список правил с более короткими формулировками того же самого, чтобы можно прочесть пару раз и запомнить:

1. Хуки только на верхнем уровне, без условий и циклов.
2. Если можно вычислить из props/state в рендере, не клади в state и не синхронизируй через useEffect.
3. Всё, что эффект читает из внешних источников данных пишите в массиве зависимостей.
4. Не используйте объекты и функции в зависимостях, иначе бесконечный цикл.
5. Эффект, который что-то запускает, должен это останавливать это в cleanup.
6. Любой асинхронный вызов в эффекте с флагом отмены или AbortController.
7. Старайтесь не использовать setState в эффекте.
8. Не мемоизируйте просто так, мемоизируйте ради оптимизации.

#### Вместо заключения

Хуки - это, конечно, мощный инструмент, который пришел на замену старых lifecycle-методов, но эта их мощь требует соблюдения дисциплины. Большинство описанных проблем сводится всего к трём вещам: неправильное понимание сути хуков, некорректное использование зависимостей и отсутствие очистки. В целом, если запомнить хотя бы описанные выше правила, то проблем с хуками у вас не будет. А если уж так лень что-то запоминать, то включите eslint-plugin-react-hooks с правилами exhaustive-deps и rules-of-hooks, и пусть линтер думает за вас :)
