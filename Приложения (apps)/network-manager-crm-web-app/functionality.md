# Функциональность Radar CRM

## Назначение проекта

- Radar CRM — mini CRM для управления проектами, работниками, сметами, отчётами, финансами и инструментами в формате мобильного веб-приложения / Telegram Mini App.
- Проект состоит из Go backend на Gin, PostgreSQL, React frontend на TanStack Start/Router, TanStack Query и интеграции с Telegram Bot API.
- Frontend работает с REST API backend через `/api/v1`; в dev-режиме Vite проксирует `/api` на backend.
- Авторизация выполняется через email + пароль или через Telegram WebApp `initData`.
- JWT access token хранится в `localStorage` под ключом `crm_token` и автоматически добавляется в заголовок `Authorization: Bearer ...`.

## Роли и доступ

- `manager` — основной пользователь CRM. После входа попадает в менеджерскую зону `/` и видит нижнюю навигацию: главная, проекты, работники, финансы, отчёты, сметы, инструменты.
- `worker` — работник. После входа попадает в `/worker`, видит отдельную worker-навигацию: главная, проекты, отчёты, документы, профиль.
- `supervisor` — роль работника с расширенными обязанностями на проекте: может создавать ежедневные отчёты супервайзера по проектам, где назначен супервайзером.
- В системе есть два близких понятия супервайзера: глобальная роль пользователя `supervisor` и роль `supervisor` внутри назначения на конкретный проект. Их нужно проверять отдельно, потому что назначение на проект не обязательно меняет глобальную роль пользователя.
- Пользователи со статусом `pending` после регистрации проходят onboarding, если не заполнены должность/специализация, затем попадают на экран ожидания подтверждения.
- Пользователи со статусом `blocked` или неактивным статусом не допускаются в рабочую зону.

## Аутентификация и onboarding

- Страница `/auth/login` поддерживает вход по email и паролю; по умолчанию в форме подставлены dev-данные `admin@example.com` / `admin12345`.
- В Telegram Mini App приложение пытается автоматически войти через `Telegram.WebApp.initData`; также показывается кнопка Telegram-входа.
- Страница `/auth/register` регистрирует нового пользователя как `worker`; после регистрации пользователь получает статус ожидания и должен быть одобрен менеджером.
- Страница `/onboarding` собирает профиль работника: должность, специализацию, ставку и другие данные, необходимые перед отправкой на подтверждение.
- Страница `/pending-approval` показывает ожидание одобрения, позволяет обновить статус пользователя и выйти из аккаунта.

## Главная менеджера

- Главный экран менеджера показывает быстрые действия: создать проект, добавить работника, получить ссылку приглашения, отправить уведомление, создать смету, добавить инструмент.
- Блок срочных действий агрегирует проблемы: новые заявки работников, неподтверждённые назначения, отчёты на проверке, проблемы/простои на объектах, просроченные отчёты, инструменты, требующие внимания.
- Есть фильтры срочных действий по уровню важности: все, красные, жёлтые, синие.
- Ниже отображается лента последней активности из backend.
- Менеджер может вручную отправить уведомление пользователю по UUID с заголовком и текстом.

## Проекты и клиенты

- Раздел `/projects` переключается между списком проектов и списком клиентов.
- Проекты фильтруются по статусу `active`, `done`, `archive`, по клиенту и поисковой строке.
- Клиентов можно искать и создавать по названию.
- Создание проекта доступно через отдельный диалог; проект может быть связан со сметой и клиентом.
- Карточка проекта `/projects/:projectId` содержит вкладки: обзор, работники, отчёты работников, ежедневные отчёты, инструменты, документы, финансы, история.
- В обзоре проекта отображаются базовая информация, клиент, супервайзер, бюджет, расходы, количество работников, подтверждения, отчёты на проверке и проблемные состояния объекта.
- Проект можно редактировать: менять статус объекта, часы простоя и бюджет.
- По проекту можно отправлять уведомления всем назначенным работникам.
- Во вкладке работников видны супервайзер и команда проекта, статусы подтверждения, возможность отправить напоминание о приглашении.
- Во вкладках отчётов менеджер видит связанные weekly-отчёты работников и daily-отчёты супервайзеров.
- Вкладки документов и истории частично выглядят как заготовки интерфейса; часть данных там пока может быть плейсхолдером.

## Работники

- Раздел `/workers` показывает работников по вкладкам: требуют одобрения, действующие, заблокированные, ресурсы.
- Доступны поиск, фильтр по специализации и фильтр по проекту.
- Вкладка ресурсов показывает загрузку по специализациям: всего, свободны, заняты на проектах, ожидают одобрения.
- Карточка работника `/workers/:workerId` показывает профиль, документы, проекты, отчёты и финансы.
- Менеджер может одобрить работника, заблокировать и разблокировать его.
- Часть вкладок карточки работника сейчас отображает статические или пустые данные: документы, проекты, отчёты, финансы.

## Сметы

- Раздел `/estimates` показывает сметы по статусам: черновики, отправленные, согласованные, отклонённые.
- Есть поиск по названию сметы, компании и городу.
- Можно создать новую смету или открыть существующую.
- Редактор сметы поддерживает основные данные клиента/проекта, тип проекта `estimate` или `outstaff`, комментарий и конструктор блоков.
- В смету можно добавлять блоки услуг, ресурсов, дополнительных расходов и прочего; блоки можно переупорядочивать и удалять.
- Сумма сметы считается на клиенте на основе блоков.
- Смету можно сохранить, изменить статус, сохранить как шаблон, создать из шаблона, экспортировать в PDF/XLSX и преобразовать в проект.

## Отчёты

- Раздел менеджера `/reports` разделён на отчёты работников и отчёты супервайзеров.
- Отчёты работников фильтруются по статусу, клиенту, проекту, работнику и поиску.
- Детальная страница weekly-отчёта показывает период, проект, работника, часы по дням, описание работ, дополнительные расходы, вложения и расчёт суммы.
- Менеджер может принять weekly-отчёт или вернуть его работнику с обязательным комментарием.
- Ежедневные отчёты супервайзеров фильтруются по проекту, супервайзеру и состоянию: на проверке, принят, есть проблема, есть простой.
- Детальная страница daily-отчёта показывает дату, проект, супервайзера, статус объекта, текстовое описание, транскрипцию голосового сообщения, часы простоя и комментарий менеджера.
- Менеджер может принять daily-отчёт, отметить его как требующий внимания и сохранить комментарий.

## Рабочая зона работника

- Главная `/worker` показывает приветствие, быстрые действия, активные проекты, ожидающие подтверждения назначения и возвращённые отчёты.
- Раздел `/worker/projects` показывает проекты работника; назначения со статусом ожидания можно подтвердить.
- Раздел `/worker/reports` переключается между еженедельными отчётами и ежедневными отчётами, поддерживает фильтры по статусу и проекту.
- Работник может создать weekly-отчёт `/worker/reports/new` по активному проекту.
- В weekly-отчёте заполняются часы по дням, описание работ и дополнительные расходы.
- Супервайзер может создать daily-отчёт `/worker/daily-reports/new` по проекту, где он назначен супервайзером.
- Daily-отчёт поддерживает статус объекта, описание, проблему/простой, часы простоя и текст для транскрипции.
- Профиль `/worker/profile` показывает персональные данные, статус, ставку, должность, специализацию, позволяет сменить язык `ru`/`en` и выйти.
- Раздел документов работника существует в навигации, но его фактическая наполненность зависит от backend-данных и текущей реализации UI.

## Финансы

- Раздел `/finance` доступен менеджеру и показывает вкладки: обзор, проекты, работники, категории.
- В обзоре отображаются бюджет, выплачено, остаток, активные проекты, расходы по категориям и топ проектов по расходам.
- Финансовые данные считаются по backend-агрегациям и принятым отчётам.
- Можно фильтровать финансовые данные по клиентам.
- В проектной карточке есть вкладка финансов, где отображается бюджет, расходы и связанные финансовые показатели проекта.

## Инструменты

- Раздел `/tools` ведёт учёт оборудования и инструментов.
- Список фильтруется по вкладкам: все, доступные, на проекте, требуют внимания, просроченные, списанные.
- Доступен поиск по названию, серийному номеру и типу инструмента.
- Новый инструмент создаётся через пошаговую форму: базовые данные, тип контроля, подтверждение.
- Поддерживаются два типа контроля: калибровка и лимит использований.
- Карточка инструмента `/tools/:toolId` показывает статус, тип, серийный номер, текущую выдачу, калибровки, лимит использований, документы/фото и историю.
- Инструмент можно назначить на активный проект, вернуть с проекта и записать новую калибровку.

## Документы, уведомления и активность

- Backend содержит модуль документов: список, загрузка, скачивание, замена и удаление файлов.
- Документы привязываются к сущностям проекта/работника/отчёта и хранятся в upload-директории backend.
- Уведомления доступны через API: список уведомлений, отметка как прочитанных и ручная отправка менеджером.
- При наличии `TELEGRAM_BOT_TOKEN` backend может отправлять уведомления через Telegram.
- Backend ведёт activity log, который используется на главной менеджера и в dashboard-агрегациях.

## Backend и данные

- Backend запускается как REST API на Go/Gin, подключается к PostgreSQL через `DATABASE_URL`.
- Основные сущности базы: users, clients, estimates, estimate_blocks, estimate_templates, projects, project_workers, reports_worker, report_expenses, reports_supervisor, tools, tool_assignments, tool_calibrations, documents, notifications, activity_logs.
- API описан в `backend/docs/swagger.yaml`.
- Миграции находятся в `backend/migrations`.
- Docker Compose поднимает PostgreSQL и API; Redis описан отдельным профилем `with-redis`.
- Есть seed-команда для создания менеджера `admin@example.com` / `admin12345`, если такого пользователя ещё нет.
- В backend работает scheduler для фоновых проверок: просроченные отчёты, инструменты, калибровки и уведомления.

## Текущее состояние реализации

- Основной пользовательский интерфейс ориентирован на мобильный формат и Telegram Mini App.
- Большая часть разделов завязана на реальные API-запросы backend и TanStack Query.
- Некоторые элементы интерфейса пока являются заготовками или неполной реализацией: отдельные кнопки без действия, статические документы в карточке работника, пустые вкладки истории/части проектных данных.
- Клиент вызывает `POST /auth/logout`, но если backend-роут logout не зарегистрирован или недоступен, frontend всё равно очищает локальный JWT в блоке `finally`; это стоит учитывать при тестировании выхода.
- Для полноценной проверки нужен запущенный backend, применённые миграции и тестовые данные: минимум активный менеджер, несколько работников, клиент, проект, смета, назначение работника на проект, отчёты и инструменты.
